## First-use experience

- **Installation/discovery friction:** real. `glomeris` is not on `PATH`, no Homebrew formula/tap, no installer — the only path today is: download the release tarball, verify its `.sha256`, extract, and either run it by full path or manually copy it onto `PATH`. There is no `glomeris daemon install`-style guided first-run either; a new user has to already know the CLI's shape.
- **CLI discoverability:** mixed. `glomeris --help` is complete and correctly lists every subcommand including `llm-plan`. But `glomeris <badcommand>` — the more likely first mistake for someone still learning the tool — prints a *different*, shorter usage string that omits `llm-plan` entirely (confirmed live against this exact binary; matches the already-filed HORO-1034, not a new finding). A user who fat-fingers a subcommand name and reads the resulting usage line would not learn that `llm-plan` exists.
- **Command naming:** coherent — `detect`/`explain`/`clean`/`free`/`emergency`/`llm-plan`/`daemon` all read as what they do. No confusing naming found.
- **Output readability:** good for both `detect` and `llm-plan`. Compact, one line per candidate, kind + resource id + estimated size + policy label + reasons. The `--json` shape mirrors the text output field-for-field, which makes cross-checking the two trivial.
- **Latency/perceived responsiveness:** the *first* `detect --project-root` invocation took 3 minutes 40 seconds wall-clock (33.5s system time, 17% CPU — I/O/scheduling-bound, not CPU-bound). Traced this to a real, severe, **pre-existing host issue** already documented on this machine before this session (`~/CLAUDE.md`): a runaway Xcode process pinned at ~162% CPU, running continuously since the prior Sunday (`ps aux` confirmed it was still present, unrelated to anything Glomeris did). Subsequent `llm-plan` invocations against the same real discovery path completed in low single-digit seconds, consistent with host load fluctuating rather than a Glomeris-side regression. This is an environmental confound on this specific dogfood machine, not attributed to Glomeris — but it's recorded here because a first-time user on a loaded machine could have the same bad first impression, and there is no progress indicator during a long `detect`/`llm-plan` discovery pass to signal it's still working rather than hung.
- **What was immediately understandable:** the policy labels (`AUTO_SAFE`, `UNKNOWN_INCOMPLETE`) and the `reasons` list next to each — e.g. `evidence_fresh_and_complete,regenerable_by_tool,no_active_use_observed` for the Homebrew cache read as a real justification, not a black box.
- **What required reading docs/source to understand:** the exact `LlmPlanItem` JSON schema for `--plan-file` (field names `resource_id`/`action_id`/`priority`/`reason`) is not documented with a concrete example anywhere in `book/src/byok.md` — had to read `src/actions/llm.rs`'s struct definition directly to construct a valid fixture. Also had to read `src/actions/homebrew.rs` to find the real registered action id string (`homebrew.cleanup.cache`) since no command exists to list registered action ids.

## Product-value observations

- **What genuinely felt useful:** the `[AUTO_SAFE]`/`[UNKNOWN_INCOMPLETE]` labeling with named reasons on real discovered candidates (Xcode DerivedData, Homebrew cache, Docker build cache) — this is a real, legible answer to "why does the tool think this is safe/not-safe" that a plain `du -sh` never gives you. The `llm-plan` banner ("advisory only, nothing is executed by this command") is exactly the right trust signal at exactly the right place — it's the first line of output, not buried.
- **What felt redundant versus existing tools/manual workflows:** for a single real project root with only Homebrew/Xcode/Docker candidates and no Cargo/Node targets present, `detect` didn't surface anything a `brew cleanup -n` / `docker system df` / manual DerivedData check wouldn't already show — the value is concentration and consistent policy labeling across tools, not new information the tools themselves don't already expose.
- **Whether Evidence/AUTO_SAFE/ASK/PROTECTED improved trust:** yes, for the one real AUTO_SAFE case exercised (Homebrew cache) the `reasons` array made the classification legible rather than asserted. `PROTECTED` and `ASK` were **not** exercised live in this pass — per the already-documented, pre-existing limitation (`book/src/known_limitations.md`), no live detector on this real machine ever emits a resource matching a `policy::protected` pattern, so there was no real opportunity to observe a live `PROTECTED` refusal end-to-end through the shipped CLI during ordinary use. This is a known gap, not a new finding, but it does mean a real user dogfooding today will likely never see the strongest safety property in action unless they specifically go looking for it (as the HORO-1008 integration test does with a fixture).
- **Whether project/process awareness materially changed decisions:** `--project-root` scoping worked as documented (it only affects Cargo/Node target discovery; Homebrew/Xcode/Docker are always machine-wide regardless of `--project-root`, which is documented behavior, not a bug, but easy to miss on first read — a user could reasonably expect `--project-root` to scope *everything*).
- **Whether `llm-plan` added useful value beyond deterministic behavior:** the one live call recommended exactly the one `AUTO_SAFE`, real-registered-action candidate (the Homebrew cache) out of three discovered candidates, correctly ignoring the two `UNKNOWN_INCOMPLETE` ones. That is a sensible, safe recommendation — but it is also exactly what a simple rule ("recommend the highest-reclaimable `AUTO_SAFE` item with a registered action") would have produced with zero API cost and zero network dependency. This single call is not enough evidence either way on whether the LLM step adds judgment beyond what deterministic ranking already provides; it would take a case with multiple `AUTO_SAFE` candidates of comparable size, or ambiguous/conflicting evidence, to actually test whether the model's ranking outperforms simple heuristics.

## Safety/trust observations

- Nothing observed made a destructive action feel unsafe — no destructive action was exercised in this pass (deliberately: the goal was a quick, low-cost pass, and this campaign's existing test suite already covers destructive-path safety extensively; re-testing it here would not have been "quick" or "low-cost").
- The live `llm-plan` call was independently confirmed non-destructive: the real Homebrew cache directory was checked before and after (`du -sh ~/Library/Caches/Homebrew`) and was untouched (still ~1.0 GB), consistent with the advisory-only design.
- No surprising classifications: all three real candidates' policy labels/reasons matched what their evidence should produce (Xcode DerivedData and Docker build cache both correctly `UNKNOWN_INCOMPLETE` per the documented "Docker/Xcode correlation can't reach Complete" limitations; Homebrew cache correctly `AUTO_SAFE`).
- False precision: the two `detect` runs in this pass reported **different** byte estimates for the same Xcode DerivedData directory between invocations (155.1 MB in one run's text output, 353.5 MB in the later `--json` run, moments apart, nothing on disk changed in between). This is the documented, intentional behavior of the budget-truncated size estimator (HORO-1016: a 750ms/200k-entry budget yields a truthful partial-sum lower bound, and different runs truncate the walk at different points depending on I/O scheduling) — not a new defect. But the CLI output gives no visible signal *at the point of display* that a given number is a truncated lower bound rather than an exact count; a user comparing two `detect` runs a minute apart would reasonably read the swing as a bug rather than "the walk didn't finish either time." (`Evidence::push_source`'s provenance note exists per the HORO-1016 changelog entry but did not visibly surface in either the human or `--json` `detect` output exercised here — worth someone checking whether that note is actually wired into `DetectCandidateReport`, or is currently write-only.)
- `policy authority vs. LLM advice`: clearly separable in the design (the banner, the fact that `llm-plan` never executes, and the fact that a real PROTECTED refusal is provable per HORO-1008's own integration test) — but this pass could not observe the LLM-advice-overridden-by-policy case live, for the same live-PROTECTED-unreachability reason noted above.

## UX observations

- CLI friction: the single-line `--help` usage string is dense (one unbroken line covering all 8 subcommands and their flags) — readable once, but not skimmable. No per-subcommand `--help` exists (e.g. `glomeris llm-plan --help` is rejected as an unrecognized argument, not treated as a request for subcommand-specific help).
- Information density: appropriate for `detect`'s output; appropriate for `llm-plan`'s output. Neither felt noisy or under-informative for the real candidate counts seen (3 candidates).
- Missing interaction affordances: no command lists registered action ids (had to read source to find `homebrew.cleanup.cache`); no command prints the exact `LlmPlanItem` JSON schema (had to read source); `--help` doesn't accept a subcommand argument for more detail.
- Whether an interactive TUI/menu-bar/native UI would materially improve the workflow: **not concluded here.** The actual friction observed in this pass was (a) no install path onto `PATH`, (b) a dense single-line help string, (c) no schema/action-id discovery command, and (d) no visible progress indicator during a long real-machine scan. All four are solvable by CLI-only means (a package/formula, multi-line `--help` formatting, a `glomeris actions list`-style command, a progress spinner) with no evidence a GUI is required to fix any of them. This section deliberately does not conclude "we need a GUI" — that would not follow from anything observed.

## Findings

### Finding 1 (already tracked, re-confirmed live — non-blocking)
- **Observation:** `print_usage()` (shown on `glomeris <badcommand>` or a subcommand parse error) omits `llm-plan` from its command list, while the separate `--help`/`-h`/`help` usage string correctly includes it.
- **Reproduction:** `glomeris badcmd` on the real v0.2.0 release binary → usage line has no `llm-plan`. `glomeris --help` on the same binary → usage line has `llm-plan`.
- **Severity:** cosmetic/discoverability only. The subcommand itself dispatches and works correctly.
- **Jira ticket:** HORO-1034 (filed during v0.2.0 release verification, before this dogfood pass). Not re-filed; confirmed still present and still accurately described.
- **Blocking:** No.

### Finding 2 (new, non-blocking — recorded, not filed as a ticket)
- **Observation:** the size-estimate lower-bound/truncation behavior (intentional per HORO-1016) produces visibly different byte counts for the same on-disk resource across consecutive `detect` runs, with no indication in the CLI output itself that the number is a truncated partial sum rather than a settled measurement.
- **Reproduction:** ran `glomeris detect --project-root ~/Bryant-Developments/glomeris` twice within a few minutes with nothing on disk changing; Xcode DerivedData reclaimable estimate read 155.1 MB in the first run's text output and 353.5 MB in the second run's `--json` output.
- **Severity:** UX/trust nitpick, not a correctness defect — the documented semantics (truthful lower bound, never an overclaim) are honored; only the user-facing legibility of "this number may still be climbing" is missing from the CLI surface itself.
- **Jira ticket:** none filed. This is a subjective-usability observation, not a reproducible correctness/safety defect, and the ticket did ask to file tickets only for the latter category. Recording it here for whoever picks up the next round of hardening to decide whether it's worth a small ticket.
- **Blocking:** No.

No release-blocking issue was found in this pass.

## Cost

- OpenAI calls: 1.
- Approximate API cost: not computable from information available to this pass (no per-call token/cost logging in Glomeris itself; the account's own usage dashboard was not checked). Input was three small structured evidence records with no file contents; output was one short recommendation — almost certainly a fraction of a cent on any current-generation model, but stated as an estimate, not a measured figure.
- Whether the LLM step appears economically reasonable for normal use: on the evidence of one call, yes — the request size is inherently small (a handful of structured fields per discovered candidate, not raw filesystem data), so per-invocation cost should scale with candidate count, not with disk size. Not enough data from a single call to state this with confidence beyond "nothing in this one observation suggests a cost problem."

## Verdict

**READY_FOR_NEXT_STAGE**

Rationale: zero release-blocking defects found; the one known non-blocking gap (Finding 1) is already tracked; the CLI's core safety semantics (advisory-only `llm-plan`, legible `AUTO_SAFE`/`UNKNOWN_INCOMPLETE` reasoning, verified non-destructive live behavior) held up under real use exactly as documented. The genuinely open question is *product* value (is `llm-plan` worth its complexity beyond a simple heuristic, is `detect`'s output differentiated enough from existing tools to matter) rather than *safety/correctness* — which is a next-product-planning question, not a harden-first blocker.

## Recommended next experiment

The smallest evidence-producing next step is **not** a new feature: point `detect`/`llm-plan` at a real project root that actually has a Cargo `target/` or `node_modules` directory present (this pass's target repo had neither, since the workspace's own build artifacts had already been cleaned up during release verification) — that would exercise the project-scoped detectors this pass could not, and would produce a multi-candidate `AUTO_SAFE` set large enough to actually test whether `llm-plan`'s LLM-backed ranking differs meaningfully from simple deterministic ranking (the open question raised above), rather than trivially agreeing with it as in this pass's single-candidate case.

## Explicitly not tested / uncertain

- Live `PROTECTED` refusal through the real CLI end-to-end (architecturally unreachable via real detectors today, per documented limitation — only provable via the HORO-1008 fixture-based integration test, not via ordinary `detect`/`llm-plan` usage).
- `ASK` classification and its (currently nonexistent) interactive handling.
- Destructive execution (`clean`/`free`/`emergency`) — deliberately not exercised in this quick, low-cost pass.
- `daemon install`/`run` — deliberately not installed for this pass, per instruction.
- Behavior against a project root containing a real Cargo `target/`/`node_modules` (none was available on this machine at pass time — see "Recommended next experiment" above).
- Exact API request/response byte size and dollar cost for the one live `llm-plan` call — not instrumented, only estimated qualitatively.
- Whether `llm-plan`'s live ranking differs from simple deterministic heuristics on a case with more than one plausible `AUTO_SAFE` candidate (this pass only had one).
- Behavior under normal (non-contended) host load — this pass's one slow `detect` run coincided with a known, pre-existing, unrelated runaway process on this specific machine; latency on a quiet machine was not separately measured.
