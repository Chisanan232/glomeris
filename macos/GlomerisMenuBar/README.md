# GlomerisMenuBar

A macOS menu-bar app (SwiftUI, `MenuBarExtra`, macOS 13+) that is a **thin
client** over the existing Rust `glomeris` CLI's `--json` output.

See the standing project rule at the top of
`Sources/GlomerisMenuBarApp.swift` — it applies to every file added to this
target, now and in the future: **no policy/evidence/action/execution logic
belongs in this Swift codebase, ever.** That logic lives in the Rust crate
under `src/` at the repo root and is reached only by spawning the `glomeris`
binary and parsing its JSON output (a later ticket — see HORO-1043 /
HVDL-26 — not this one).

## Scope of this skeleton (HORO-1059)

- Menu-bar icon (SF Symbol placeholder) via `MenuBarExtra`.
- Clicking it opens an empty popover.
- `LSUIElement = true` — no Dock icon, no app switcher entry.
- No networking, no `Process` spawning, no data model, no candidate list.
  That is all explicitly out of scope and lands in follow-up tickets.

## GlomerisClient (HORO-1060)

`Sources/GlomerisClient.swift` is the generic spawn/decode plumbing this
skeleton was missing: it spawns the `glomeris` binary via
`Process.executableURL` + `arguments` only (never a shell), decodes stdout
as a single caller-supplied `Decodable` type, decodes stderr as
newline-delimited JSON progress lines, and surfaces the CLI's exit-code
conventions (see `book/src/cli_reference.md`) as typed
`GlomerisClientError` cases. It does not call any specific subcommand or
know any specific DTO shape — wiring it to `detect`/`status`/etc. is later
UI tickets' job. Binary path resolution is a placeholder (see the `TODO`
on `GlomerisClient.defaultExecutableURL`) — finding the real
embedded/installed binary is out of scope here.

## Project layout

```
macos/GlomerisMenuBar/
├── project.yml                       # XcodeGen spec (source of truth for the project)
├── GlomerisMenuBar.xcodeproj/        # Generated by XcodeGen, committed so CI needs no extra tooling
├── Sources/
│   ├── GlomerisMenuBarApp.swift      # @main entry point — standing project rule lives here
│   ├── GlomerisPopoverView.swift     # Empty popover content
│   ├── GlomerisClient.swift          # Generic spawn/decode plumbing over the `glomeris` binary (HORO-1060)
│   └── Info.plist                    # Generated by XcodeGen from project.yml; committed
├── Tests/
│   └── GlomerisClientTests.swift     # GlomerisMenuBarTests unit test target
└── README.md
```

`GlomerisMenuBar.xcodeproj` is generated with [XcodeGen](https://github.com/yonaskolb/XcodeGen)
from `project.yml` and then committed, so a clean checkout builds via
`xcodebuild` alone — regenerating with XcodeGen is only needed when
`project.yml` changes (new source files, new settings), not for every build.

## Building

```sh
xcodebuild -project macos/GlomerisMenuBar/GlomerisMenuBar.xcodeproj \
  -scheme GlomerisMenuBar -configuration Debug build CODE_SIGNING_ALLOWED=NO
```

Code signing is disabled (`CODE_SIGNING_ALLOWED=NO` / `CODE_SIGNING_REQUIRED=NO`
in `project.yml`) so this builds on a clean checkout / CI runner with no
Apple Developer account or signing identity configured.

**A recent Xcode is required.** The committed project is `objectVersion = 77`,
and an Xcode too old for that format refuses to open it at all rather than
degrading gracefully: Xcode 15.4 reports "a future Xcode project file format
(77)" and exits 74 without reading the project. XcodeGen chooses the format, so
it is not something `project.yml` can lower. Measured: 15.4 fails, 26.2 (what
CI pins) works — the exact lower bound in between has not been established.

## Regenerating the Xcode project

Required after editing `project.yml` (e.g. adding a new source file or target
setting) — CI enforces it, see below. The simplest way is to run the guard,
which regenerates in place:

```sh
bash scripts/check-xcodeproj-matches-xcodegen.sh
git add macos/GlomerisMenuBar/GlomerisMenuBar.xcodeproj
```

Or directly:

```sh
cd macos/GlomerisMenuBar
xcodegen generate --spec project.yml
```

Use the XcodeGen version pinned in
[`.xcodegen-version`](.xcodegen-version). Different versions emit different
`project.pbxproj` bytes for the same spec, so `brew install xcodegen` (which
tracks whatever is current) will eventually produce a project that differs from
the committed one for toolchain reasons alone. The guard checks the version on
`PATH` and refuses to run on a mismatch rather than reporting phantom drift.

## What CI enforces (HORO-1296)

`.github/workflows/ci.yml` has two macOS jobs for this app:

- **`macos-app`** builds the `glomeris` CLI, then runs the `GlomerisMenuBar`
  test scheme. It is not path-filtered to `macos/**`: the DTO golden-fixture
  tests decode `tests/fixtures/dto/` at the repo root, shared with the Rust
  suite, so a Rust-side change can legitimately break the Swift mirrors. The
  CLI is built first because one test `XCTSkip`s without it.
- **`xcodeproj-drift`** regenerates with the pinned XcodeGen and fails if the
  committed project differs.

Both run on `macos-15`. `macos-app` additionally selects Xcode 26.2
explicitly rather than taking the image default, for two reasons:
`MenuBarAppearanceTests.testSystemImageNameResolvesOnThisOS` asserts an SF
Symbol resolves on the running OS, so the toolchain is part of what the job
asserts; and 26.2 is the version the app is developed and dogfooded against.
`xcodeproj-drift` needs no Xcode pin — it never runs `xcodebuild`, and
XcodeGen's output was observed not to depend on the installed Xcode.
